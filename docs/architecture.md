# MyTrakin — Platform Architecture

Status: Phase 1 (Foundation) — this document is the authoritative blueprint. It is written to
be extended, not rewritten, as later phases land.

## 1. Guiding decisions (the "why" behind the structure)

| Decision | Rationale |
| --- | --- |
| API-first, no business logic in the browser | Financial and authorization correctness cannot depend on a client that can be tampered with. All computations (money, allocation, entitlement, RBAC) execute server-side in SQL or Python. |
| UUIDv7 internal PK + immutable human-readable `public_id` | UUIDv7 is time-ordered (good index locality at 1M+ rows) and non-enumerable. `public_id` gives supportable IDs without leaking row counts. Public IDs are generated by the database and never mutated (enforced by trigger). |
| Supabase Auth owns credentials; the API owns authorization | Supabase Auth handles password/Google/email-verification/MFA primitives. It knows nothing about companies, roles or resources. Authorization lives in PostgreSQL RLS + FastAPI RBAC, so it cannot be skipped by calling Supabase directly. |
| RLS is evaluated as the *end user* | The API connects as a non-superuser role and sets `app.user_id` / `app.company_id` on every transaction. Policies therefore see the caller's real identity. A bug in application code degrades to "no rows", never "all rows". |
| Explicit DB roles: `mytrakin_api`, `mytrakin_worker`, `mytrakin_migrator` | Least privilege is structural. Workers can process jobs but cannot impersonate a user; the API can act for a user but has no schema DDL rights. |
| Permissions live in tables, never in code | `permissions` / `role_permissions` / `company_roles` are data. A new role is created by an admin in the UI, not a deploy. `app.has_permission()` is the single decision function. |
| Money is `NUMERIC(18,4)` + ISO-4217 `CHAR(3)` | No floats anywhere. Every amount carries its currency; FX pairs store rate + original + converted amount for auditability. |
| Financial writes are idempotent | `idempotency_keys` is a first-class table; invoice generation, payments, bank sync and webhooks all require a key. |
| Events are transactional outbox rows | Domain writes and their events commit together, so "invoice created" can never be lost or duplicated relative to the invoice itself. A dispatcher publishes to Celery/Redis. |
| AI is a gateway, not a vendor | `apps/api/app/ai` defines `ChatProvider`/`EmbeddingProvider` protocols with OpenAI, Anthropic, Gemini and local adapters. Routing, budgets, caching and audit live in the gateway. Application code never names a vendor. |
| AI retrieval is permission-filtered *before* context assembly | `app.ai_visible_chunks()` is a SECURITY DEFINER function that filters by the caller's company + permission. Unauthorized content never enters the prompt. |
| Humans approve consequential AI output | `ai_actions` records proposal → human approval. Extraction results are staged (`ai_extractions.status = PENDING_REVIEW`) and applied by explicit user action. Agents cannot call mutating tools without a capability token bound to a user. |
| PII minimization by default | Sensitive values (TIN, SSN, bank tokens) live in separate tables with their own RLS, are masked at the API boundary, and are never logged, put in URLs, or sent to analytics. |

## 2. Runtime topology

```text
Browser
  │  Supabase Auth (session cookie / PKCE)
  ▼
Azure Front Door (WAF, CDN, TLS, DDoS)  ──►  static assets via CDN
  ▼
Next.js (apps/web)  — SSR shell, design system, server components
  │  HttpOnly session JWT + X-Request-Id
  ▼
FastAPI (apps/api) /api/v1
  ├── Supabase Auth JWKS verification (local, no network hop per request)
  ├── RBAC + company-context resolution
  ├── Domain services + authorization
  ├── Redis: cache, rate limits, Celery broker
  └── AI Gateway ──► OpenAI / Anthropic / Gemini / local
  ▼
Supabase
  ├── PostgreSQL 16 + RLS  (the only source of truth)
  ├── Auth        (identity only)
  ├── Storage     (private buckets, signed URLs only)
  ├── pgvector    (RAG chunks, HNSW)
  └── Realtime    (notifications, messenger)
```

External adapters (server-side only): Plaid, payment processor, email/SMS provider, OCR,
SFTP. Each is an interface + a provider registry so a missing credential disables the feature
with a typed `IntegrationNotConfigured` error rather than a fake success.

Cross-context access is by **foreign key only**. There is no shared mutable table between
CORE and PAYMENTS; they meet at `invoices` and `payments`, both of which are append-audited.

## 4. Identity, tenancy and the request pipeline

1. Browser holds a Supabase Auth JWT (HttpOnly, `SameSite=Lax`, `Secure`).
2. `apps/web` forwards it to FastAPI. Frontend never receives the service-role key.
3. `AuthContext` middleware verifies the JWT against Supabase JWKS (cached, rotated), extracts
   `sub` (auth uid) and `email_verified`, and rejects unverified accounts (403 `EMAIL_NOT_VERIFIED`).
4. `CompanyContext` middleware resolves `X-Company-Public-Id` → `company_id` via membership,
   or the header is ignored. Membership alone grants nothing further; permission checks come next.
5. `db.session` opens a transaction on `mytrakin_api` and issues
   `SET LOCAL app.user_id`, `SET LOCAL app.company_id`, `SET LOCAL app.request_id`,
   `SET LOCAL app.actor_type`. **Every** query in the request runs under these.
6. `require_permission("contracts.approve")` → `app.has_permission(company_id, key)`.
7. `audit()` writes an `audit_logs` row inside the same transaction as the mutation, so an
   audit record cannot exist without the change (or vice versa).
8. Middleware attaches `X-Request-Id`; errors return the standard envelope with that ID.

| Entity | Format | Example |
| --- | --- | --- |
| User | `U` + 8 base32 | `U8K29F4A7` |
| Company | `CO` + 8 | `CO3M7QK2D` |
| Project | `P` + 8 | `P7D2K9QX4` |
| Role | `R` + 8 | `R5K8M1ZV3` |

| Contract | `C` + 8 | `C6J3W8NR5` |

Implemented as `app.gen_public_id(prefix)` + an immutability trigger on each `public_id` column.

## 5. Authorization model

```text
User ──▶ CompanyMembership ──▶ CompanyRole ──▶ RolePermission ──▶ Permission
             (status)              (company)         (role)            (key)
```

- Permission keys are dotted, namespaced, seeded by migration, e.g. `contracts.approve`.
- System roles are seeded per company on creation (`SUPER_ADMIN`, and opt-in templates).
- `SUPER_ADMIN` is a role, not a hardcoded branch: it is granted `*` via a wildcard expansion in
  `app.has_permission`, so revoking a key from it actually revokes it.
- Segregation of duties is a policy, not a hope: `app.assert_sod()` blocks self-approval of
  timesheets, invoices and payments unless the company policy table explicitly permits it.
- Defense in depth: RLS filters rows; RBAC filters actions; a direct `curl` to the API hits both.

## 6. Security boundaries

| Boundary | Control |
| --- | --- |
| Browser → Edge | TLS 1.3, WAF rate rules, bot filter, no service keys in bundles |
| Edge → API | Supabase JWT, CORS allowlist, request size caps, `X-Request-Id` |
| API → DB | `mytrakin_api` role, `SET LOCAL` identity, RLS on every tenant table, no `BYPASSRLS` |
| API → Storage | service-role access only server-side; clients get short-lived signed URLs (≤300s) |
| API → AI | gateway-only; PII redactor; budget checks; full `ai_usage_events` ledger |
| Documents → AI | untrusted-content boundary: extracted text is data, never instructions |
| Webhooks | HMAC/JWT signature verification + replay window + idempotency key before any effect |

IDOR/BOLA posture: every external identifier in a URL is a `public_id` resolved through a
permission-scoped query. A cross-company `public_id` returns `404` (not `403`) so existence is
not leaked, and the audit log records the attempt.

### Deletion semantics

Legal and financial records are **soft-deleted** (`deleted_at`), never hard-deleted:

| Record | Policy |
| --- | --- |
| Company | soft-delete only; the API exposes `DELETE /companies/{id}` as "archive" |
| Contract, SOW, invoice, payment, timesheet, document version | immutable or soft-delete; hard delete requires a retention-elapsed purge job running as `mytrakin_worker` |
| Audit log, AI usage, bank transactions, document versions | hard delete is impossible at the database level (`app.reject_mutation()`) |

This is why some foreign keys use `ON DELETE RESTRICT`: RESTRICT is evaluated eagerly and
blocks an accidental `DELETE FROM companies` from silently destroying contracts. A legitimate
purge must delete children in dependency order, which is what
`scripts/cleanup_test_data.py` and the retention worker do.

## 7. Event flows (transactional outbox → Celery)

```text
DOCUMENT_UPLOADED      → malware scan → classify/OCR → embeddings → RAG index
TIMESHEET_APPROVED     → billing run → INVOICE_CREATED → notification + email
INVOICE_SUBMITTED      → counterparty notification
PAYMENT_DETECTED       → reconciliation engine → PAYMENT_MATCHED
CONTRACT_ACCEPTED      → assignment activation → timesheet eligibility
MSA_APPROVED           → invoice eligibility re-evaluation (unblocks DRAFT)
CONTRACT_EXPIRING      → risk alert → automation trigger
USER_SIGNED_UP         → profile bootstrap + default preferences
```

Guarantees: at-least-once delivery, every consumer keyed by `idempotency_key`, dead-letter table
`tasks`, exponential backoff, and `ai_automation_runs` for user-authored automations.

## 8. Performance plan for 1M+ users

- Keyset (cursor) pagination everywhere; `OFFSET` never above 500 rows.
- Composite indexes lead with `company_id`, then the filter/sort columns.
- Partial indexes for hot states (`WHERE status IN (...)`) — pending approvals, overdue invoices.
- HNSW vector index; `pg_trgm` + GIN for search; `tsvector` generated columns for FTS.
- Redis caches reference data, permissions and dashboard aggregates, all keyed by
  `company_id` and invalidated on the owning write.
- Connection pooling (PgBouncer, transaction mode) + `statement_timeout` per role.
- Background processing for OCR, AI, invoice generation, bank sync, reports, imports.
- No `SELECT *` in service queries; explicit column lists and projections.

## 9. Environments & release

Dev → Staging → Prod, each with isolated Supabase project, storage, Auth providers, AI keys,
Plaid keys and processor keys. Migrations are forward-only, versioned SQL applied by
`supabase db push` in CI; `db diff` validation blocks deploys on schema drift. GitHub Actions
runs lint → typecheck → unit → integration → RLS/security tests → build → migrate → deploy,
with migrations gated to protected environments.
